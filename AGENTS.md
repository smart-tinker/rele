# Работа над Rele

Перед изменением прочитайте [DEVELOPMENT](docs/DEVELOPMENT.md), а для проверок —
[CI](docs/CI.md). Архитектура: [ARCHITECTURE](docs/ARCHITECTURE.md);
приёмка готового пакета: [ACCEPTANCE](docs/ACCEPTANCE.md).
Публикация draft/RC/stable: [RELEASING](docs/RELEASING.md).
Это точка входа, не замена этим документам.

## Небольшой проверяемый шаг

- Перечитайте актуальные issue/PR и SHA; не дублируйте уже выполняемую работу.
- В issue зафиксируйте сценарий, наблюдаемый результат, ожидаемое поведение,
  in/out scope и инварианты. Каждый пункт DoD связывайте с методом проверки,
  ожидаемым результатом и evidence. Отделяйте факт от гипотезы.
- Один PR решает одну связную задачу. Сначала минимальная реализация и релевантные
  тесты; соседний рефакторинг и новые зависимости не добавляются «заодно».
- Неизвестный API/capability сначала проверьте на поддержанной версии. Не заменяйте
  неподдержанную возможность скрытым fallback, новым чатом или имитацией успеха.
- Для дефекта нужен тест, падающий на нужном assertion до исправления (RED),
  и проходящий после (GREEN). Ошибка установки/импорта не является RED.
  Для docs-only явно укажите неприменимость runtime-тестов.
- После последнего изменения повторите затронутые проверки; перед ready выполните
  обязательные итоговые gates из CI. Узкий probe не заменяет полную матрицу.

## Инварианты Rele

- Удостоверенный источник → проверка доступа → native execution → исходный адрес
  ответа. Не пересоздавайте ID разговора и не переносите запрос в другой источник.
- Повторное событие не создаёт второй запрос. Неизвестный результат enqueue/отправки
  требует сверки, а не слепого replay; не ослабляйте fail-closed/ownership guards.
- Сохранённая настройка, подключение, native-принятие, выполнение и доставка —
  разные состояния. UI не объявляет неподтверждённое состояние успешным.
- Изменяя state machine, проверьте применимые повтор, restart/reconnect, потерянный
  ACK, отмену, stale target и отказ доступа. Обоснуйте неприменимые случаи.
- Fixture/mocked delivery не доказывает реальную доставку в Slack/Telegram;
  CI не доказывает GUI/DPAPI в интерактивной сессии владельца.
- Не используйте рабочие auth/историю в тестах и не публикуйте секреты/частный
  контекст. Соблюдайте разрешённые среды и границы операций из DEVELOPMENT.

## Evidence и завершение

PR открывается draft, связывается через `Refs #…`, без `Fixes/Closes`.
В одном актуальном итоговом блоке укажите:
- точный source SHA, среду и версии инструментов;
- для каждой проверки команду/метод, ожидаемый и фактический результат, ссылку;
- статус `PASS / FAIL / UNRUN / INVALID / BLOCKED / N/A` с причиной;
- отдельно source/CI, package (версия + SHA256), installed runtime и real delivery;
- невыполненные DoD и следующий шаг.

Не переносите PASS со старого SHA на новый. Build, публикация, установка и приёмка
не взаимозаменяемы. Merge не закрывает issue: требуется принятие его DoD.
Не меняйте billing, права, настройки CI, releases или рабочие установки как
побочный эффект задачи; соблюдайте отдельное разрешение и бесплатные лимиты.
