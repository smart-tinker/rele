# Rele

Локальное приложение, которое связывает Telegram и Slack с общими разговорами Codex. Контекст хранит Codex; ответ и запрос подтверждения возвращаются в источник конкретного запроса.

Следующий кандидат: [0.1.1-rc.12 — передача Slack и продолжение после перегрузки](docs/0.1.1-rc.12.md).

## Целевой сценарий

- Windows: Rele, codex app-server и Codex Desktop на одном ПК.
- Ubuntu Server: Rele, codex app-server и Codex CLI на одном сервере.
- Один разговор Codex: несколько источников Telegram и тредов Slack.
- Общий контекст Codex; каждый ответ возвращается в источник своего запроса.
- Веб-панель показывает связи по названиям.

WSL и отдельный компонент Rele Node исключены из первого релиза.

## Выпуск

Кандидат **0.1.1-rc.12** убирает дублирующее транспортное представление Slack из контекста, сохраняет старые квитанции и продолжает подтверждённый завершённый ход после перегрузки. Он включает исправления RC11. Сборка: Windows на windows-test-host, Linux на linux-build-host. Готовые пакеты проверяются только на windows-test-host (Windows) и linux-test-host (Linux). Stable и остальные машины обновляются после приёмки. [Изменения RC.12](docs/0.1.1-rc.12.md).

Последний стабильный выпуск — **v0.1.0**. Native Windows x64 и Ubuntu Server x64, одна кодовая база и один веб-интерфейс. Текущее дерево проверяет протокол **Codex app-server 0.163.0, 0.163.0-alpha.10.2, 0.163.0-alpha.11, 0.163.0-alpha.11.2, 0.164.0-alpha.11.1, 0.165.0-alpha.1.2 и 0.166.0-alpha.5.1**. Другие версии отображаются в панели, но запись блокируется до проверки адаптера. Версия установленного CLI и версия сервера Desktop могут различаться. Результаты совместимости для конкретного commit и пакетов приводятся в описании GitHub release.

В основу 0.1.0 вошли управляемое обновление Codex, проверка простоя и очистка подтверждённых старых адаптеров. Linux использует штатный updater и отдельную службу запуска Codex. [Изменения rc.30](docs/RC30.md).

В rc.26 добавлены автоматические продолжения после перегрузки Codex, полная цепочка публичных комментариев и итог в одном сообщении Slack. Исправлена периодическая сверка параллельных запросов: неопределённое состояние больше не остаётся без проверки и честно обозначается в карточке. [Изменения и границы rc.26](docs/RC26.md).

В rc.25 исправлено обновление Windows с работающими MCP-инструментами Rele: неизменившийся runtime не заменяется, а подготовка использует собственный временный комплект установщика. Повреждённые модули старой копии больше не мешают подготовить обновление. Временные процессы и незавершённая новая резервная копия очищаются; рабочий общий Codex и его MCP не останавливаются. [Изменения и границы rc.25](docs/RC25.md).

В rc.24 на уточнения Codex можно отвечать штатными кнопками и формами Slack. Для одного вопроса доступны короткие варианты и собственный ответ; несколько вопросов открываются одной формой. Ответ продолжает исходный запрос Codex. Секретные ответы остаются в локальной панели Rele. Реальный рендеринг и управление в Slack ещё не приняты. [Изменения и границы rc.24](docs/RC24.md).

В rc.23 инструкция Rele передаётся отдельным начальным ходом один раз для исходного профиля и треда; её можно повторить кнопкой. Обычные сообщения сохраняют атрибуцию без повторного предисловия. Дополнения из того же источника попадают в выполняющийся ход Rele, режим доступа меняется сразу в таблице, а публичные комментарии и план работы отправляются в Slack штатными карточками. Реальная приёмка этих карточек в Slack ещё не подтверждена. [Изменения и границы rc.23](docs/RC23.md).

В rc.22 сообщения сохраняют автора, исходные обращения и снимок известных участников треда. Добавлены инструмент явной отправки Rele, короткий скилл и подавление ответа точным `NOREPLY`. В запросах агентов управление доступно людям исходной группы. Windows передаёт встроенным инструментам Desktop отдельное локальное соединение, сохраняя прямой WebSocket к общему серверу. [Изменения и границы rc.22](docs/RC22.md).

В rc.21 связи и доступ объединены в одной таблице Telegram/Slack; текстовые фильтры очищаются кнопкой ×. При назначении уже загруженного разговора устранён лишний полный обход истории. Windows owner общего Codex запускается без консольного окна; обновление сохраняет работающий сервер. Перегрузка Codex объясняется в исходном канале без автоматического повторения запроса; оставшийся после завершённой ошибки статус больше не блокирует следующий запрос из Slack. [Изменения и границы rc.21](docs/RC21.md).

В rc.20 Desktop подключается прямо к общему native app-server по локальному WebSocket. Между Desktop и сервером нет адаптера Rele; установщик меняет только принадлежащий Rele адрес подключения. Сервер работает независимо от панели и gateway. После Stop следующий собственный запрос в native-очереди продолжается автоматически; отменённая команда должна подтвердить остановку до запуска следующей. [Изменения и границы rc.20](docs/RC20.md).

В rc.19 установщик автоматически подготавливает общий Codex и обычный запуск Desktop, в том числе при обновлении со старого неработающего локального WebSocket. Выбирать режим и нажимать подключение в панели не требуется. Выбор отключить интеграцию сохраняется; временный отказ запуска оставляет её ожидающей готовности общего сервера. Профиль, чаты и очередь сохраняются. После первого подключения нужен один полный выход из Desktop и обычный запуск. [Изменения и границы rc.19](docs/RC19.md).

В rc.18 восстанавливается запуск общего Codex после отказа из-за унаследованных прав служебного каталога Windows: после проверок владельца, содержимого и отсутствия работающего сервера старый каталог сохраняется в backup, новый создаётся с private ACL. Панель позволяет явно повторить подключение обычного Desktop после сохранения shared, без переустановки и закрытия текущих задач. Исходные профиль, авторизация, история и настройки сохраняются. [Изменения и границы rc.18](docs/RC18.md).

В rc.17 исправлены восстановление Windows daemon при оставшемся AF_UNIX сокете и отказ обычного Desktop с точным локальным параметром `features.prefer_mxc=true`. [Изменения и границы rc.17](docs/RC17.md).

В rc.16 установщик проверяет настройки и ранний обмен Desktop с общим сервером до включения интеграции. Старый WebSocket target, отсутствующий backend или нечитаемые защищённые настройки оставляют обычный запуск Desktop без hook Rele и сопровождаются предупреждением. Прежние адрес, профиль и история сохраняются. [Изменения и границы rc.16](docs/RC16.md).

В rc.15 исправлены обычный вызов backend из Desktop с глобальными параметрами и сброс выбора интеграции установщиком при обновлении Rele. На Ubuntu обычный интерактивный `codex` использует штатный daemon без подмены команды. [Изменения и границы rc.15](docs/RC15.md).

В rc.14 для первого запуска общего Codex на Windows достаточно установленного Desktop: Rele использует его локальные компоненты без скачивания или ручной установки CLI. Проверяется комплектность одной поставки и поддерживаемая версия backend; компоненты сохраняются отдельно от обновляемой папки Desktop. [Изменения и границы rc.14](docs/RC14.md).

В rc.13 рекомендуемый режим «Общий Codex» находит штатный daemon или запускает его в исходном профиле. Подключённые Rele, Desktop и интерактивный CLI используют один сервер и исходные ID разговоров. Windows получает адаптер Desktop и отдельные пункты запуска; Ubuntu Server — независимый запуск daemon через systemd без графического окружения. Общий сервер переживает обновление Rele. Для перехода со старой ручной схемы выберите «Общий Codex» и один раз полностью перезапустите Desktop через установленный адаптер. [Изменения и границы rc.13](docs/RC13.md).

В rc.12 «Связи» показывают источники Telegram/Slack в отдельных вкладках: группа/чат → тема/обсуждение → разговор Codex. Права off/mention/all вынесены в «Доступ», новые источники выключены; несколько источников могут использовать один Codex. Добавлены явное восстановление незавершённого автосоздания и ограниченная диагностика без загрузки конфигурации, DPAPI или истории. SQLite мигрирует до v6: перед обновлением нужен backup, откат требует совместимой копии до миграции. [Изменения rc.12](docs/RC12.md).

Ранее в rc.11 исправлена загрузка личных чатов Slack: параметры каталога передаются в поддерживаемом формате, а недостающее право для одного типа чатов не блокирует остальные. Неполный каталог сопровождается пояснением о правах. [Изменения rc.11](docs/RC11.md).

В rc.10 настройки упоминаний говорят о подключённом агенте: используйте его настоящее имя в мессенджере, выбрав из списка после `@`. Кнопка «Изменить название только в Rele» задаёт локальную подпись источника. Распознавание упоминаний и права доступа не менялись. [Изменения rc.10](docs/RC10.md).

В rc.9 снято ограничение одного источника каждого мессенджера: к одному Codex-треду можно подключить несколько Telegram/Slack обсуждений. Добавлено явное автосоздание нового native треда по правилу выбранного чата, рабочего каталога и доступа; потерянный ответ `thread/start` автоматически не повторяется. Исправлено ложное завершение «остановлено в Codex» по промежуточному снимку истории без подтверждённого времени завершения. [Изменения rc.9](docs/RC9.md).

С rc.8 Slack использует Agent Sessions: `processing` при выполнении и распознавании аудио, `suspended` при ожидании подтверждения или ответа, `active` при ожидании запуска и после завершения. Штатная кнопка Stop отменяет собственный запрос через прежний защищённый механизм; команда `rele:cancel` сохраняется. Для Stop нужна подписка Slack app на `agent_session_stopped`: одного обновления Rele недостаточно. Новый manifest объявляет `agent_view`; существующие приложения обновляются вручную без автоматической миграции поверхности. Внешний вид spinner в обычных Activity/Threads пока не подтверждён. [Изменения rc.8](docs/RC8.md), [настройка Slack](docs/CHANNELS.md#slack).

С rc.6 ответы Slack используют rich Markdown с таблицами, а все доступные сообщения связанного обсуждения, включая других агентов, поступают в контекст модели. В сведениях источника есть журнал синхронизации. Выбранные боты могут запускать запрос свежим упоминанием подключённого агента. Полная синхронизация доступна в режиме «Сервер Rele» или через общий локальный сервер с тем же профилем и подтверждённой native записью. [Изменения rc.6 и границы](docs/RC6.md).

С rc.4 основной режим — собственный сервер Rele с существующим профилем Codex. Он продолжает исходные чаты без копирования и подмены ID, ждёт занятой тред и освобождает его после работы. Сохраняются штатные установщики Windows / Ubuntu, фоновый запуск, вход без копирования ключа и автоматический поиск Codex. [Изменения rc.4](docs/RC4.md). [Каталог разговоров](docs/CATALOG.md): каналы и обсуждения Slack загружаются через API; Telegram предлагает обнаруженные чаты, выбор группы у бота и регистрацию темы; Codex показывает сохранённые разговоры с поиском и просмотром архива. Telegram подключается только токеном бота.

Общая история, очередь, восстановление и подтверждения проверяются на настоящем Codex с локальным тестовым inference provider. Это не заменяет приёмку настоящего Windows Desktop и разрешённых Telegram / Slack чатов. Условия стабильного релиза: [план](docs/PLAN.md), [приёмка](docs/ACCEPTANCE.md), [issue #2](https://github.com/smart-tinker/rele/issues/2).

## Установка

Скачайте пакет для своей ОС из [GitHub Releases](https://github.com/smart-tinker/rele/releases). Node.js 24.19.0 и production-зависимости уже включены. На Windows достаточно установленного Codex Desktop; на Ubuntu требуется установленный CLI. Python и модель нужны только для локального распознавания аудио. Подробности: [установка, обновление и удаление](docs/INSTALLATION.md).

### Windows

1. Если ещё работает Rele из прежнего ZIP, завершите его в прежнем PowerShell через `Ctrl+C`.
2. Скачайте `rele-0.1.0-rc.25-windows-x64-setup.exe` и запустите его под тем же пользователем, что и Codex Desktop.
3. Завершите установку с выбранной интеграцией Desktop. Панель откроется в браузере с автоматическим входом.
4. Если Desktop был открыт до установки, дождитесь завершения задач, один раз полностью выйдите из него через трей и откройте обычным способом. Общий Codex настраивается автоматически.

Программа устанавливается в `%LOCALAPPDATA%\Programs\Rele`; данные остаются в `%LOCALAPPDATA%\Rele`. Фоновая задача запускается при входе этого пользователя в Windows. Терминал для работы Rele не требуется. В меню «Пуск» появятся «Открыть Rele», «Перезапустить Rele» и «Остановить Rele».

Для обновления запустите новый установщик. Для удаления используйте Windows → «Установленные приложения» → Rele. Удаление программы сохраняет данные. Сборки RC пока не имеют подписи издателя.

### Ubuntu Server

Под пользователем, которому принадлежит Codex:

```bash
sudo apt install ./rele-0.1.0-rc.25-linux-x64.deb
rele service status
```

Пакет устанавливает программу в `/opt/rele`, команду `rele` в `/usr/bin` и службу systemd под пользователем, вызвавшим `sudo`. Если установка выполнена напрямую из root или система развёртывания не передала владельца, один раз укажите его:

```bash
sudo rele service install --user <владелец-Codex>
```

Панель слушает только loopback. С рабочего компьютера откройте SSH-туннель:

```bash
ssh -L 3210:127.0.0.1:3210 user@server
```

В сессии сервера выполните `rele open --print-url` и откройте выданную одноразовую ссылку на рабочем компьютере. Она действует 60 секунд. Для ручного входа доступны `rele token` и `http://127.0.0.1:3210`.

Обновление: `sudo apt install ./rele-<новая-версия>-linux-x64.deb`. Удаление: `sudo apt remove rele`. Пользовательские данные сохраняются даже после `purge`. Служба работает после выхода из SSH и запускается при загрузке сервера.

ZIP / TAR с `start-rele.cmd` / `start-rele.sh` остаются для переносимого запуска. Диагностика старого CMD launcher: [эксплуатация](docs/OPERATIONS.md).

## Подключение Codex

В режиме **«Общий Codex»** доступны два варианта выбора:

- **«Максимальная поддерживаемая версия»** — самая новая из найденных установленных версий, поддерживаемых Rele. Более новая неподдерживаемая версия не вытесняет поддерживаемую.
- **«Выбрать конкретную версию»** — выбранный исполняемый файл; Rele сохраняет этот выбор и не заменяет его автоматически.

Оба варианта используют исходный профиль Codex. Windows запускает установленный native backend Desktop на постоянном адресе `ws://127.0.0.1:PORT`; отдельный CLI не требуется. Ubuntu Server использует штатный daemon установленного CLI и его UDS. Сохранение выбора версии не заменяет работающий подтверждённый общий сервер и не меняет подключение Desktop.

Страница Codex показывает работающую и выбранную версии отдельно. На Windows нажмите **«Подготовить обновление»**: Rele подготовит следующий запуск на выбранной поддерживаемой версии, а текущий сервер и работающие задачи продолжат работу. Автоматический режим выбирает максимальную поддерживаемую версию; ручной использует только выбранный файл. Понижение версии общего сервера пока блокируется: совместимость нового профиля со старым backend не подтверждена. Обновление Rele и «Обновить статус» сами по себе сервер не заменяют. Сменить выбор можно после завершения незаконченных операций Rele; уже подготовленное обновление нужно сначала завершить.

Для применения завершите задачи и полностью выйдите из Codex Desktop, CLI и остальных клиентов общего сервера. Отметьте **«Я завершил задачи и полностью закрыл Codex Desktop и CLI»** и нажмите **«Обновить Codex»**. Клиенты должны оставаться закрытыми до завершения операции. Rele приостанавливает отправку своей очереди, проверяет общий простой и отсутствие других подключений, останавливает только проверенный собственный экземпляр задачи Codex и запускает подготовленную версию с прежними адресом и профилем. После проверки нового сервера Rele переподключается и продолжает очередь; новые входящие запросы сохраняются во время паузы. Дождитесь подтверждения и откройте Desktop обычным способом. Перезагрузка Windows и UAC не требуются; Rele не закрывает внешние клиенты принудительно.

«Desktop: подключение настроено» означает сохранённую настройку запуска, а не проверку текущего окна Desktop. Параметры сервера доступны в «Настройки подключения», пути и адрес — в «Технические сведения».

Пустое поле профиля наследует `CODEX_HOME` окружения либо стандартный `~/.codex` владельца Rele. Для нестандартного Desktop-профиля укажите тот же полный путь. Панель показывает фактический профиль; авторизация и настройки остаются в Codex, Rele не переписывает `config.toml`.

На Windows установщик по умолчанию подключает обычный запуск Codex Desktop к общему серверу. Один раз полностью выйдите из уже работающего Desktop и откройте его обычным способом. Выбор интеграции сохраняется при обновлении Rele; ранее отключённая интеграция и конфликтующие чужие настройки не заменяются молча. Дополнительный пункт «Codex Desktop (общий с Rele)» остаётся для явного запуска с нужным окружением.

Если подключение Desktop было пропущено, после сохранения «Общий Codex» явно нажмите «Подключить обычный Codex Desktop» в разделе «Codex». Там же можно отключить интеграцию перед сменой сервера или профиля. Эти действия не закрывают работающие окна, не останавливают Rele и не заменяют выбранный профиль. Статус показывает настройки установки; фактическое подключение уже открытого Desktop проверяется отдельно.

Desktop обращается к серверу напрямую: установщик задаёт только пользовательский `CODEX_APP_SERVER_WS_URL`. Прежние принадлежащие Rele `CODEX_CLI_PATH`/`CODEX_APP_SERVER_FORCE_CLI` восстанавливаются по сохранённым значениям; чужие изменения сохраняются. Общие инструменты и настройки берутся из исходного профиля. Windows-сервер слушает только `127.0.0.1` без токена: к нему могут подключаться другие локальные процессы и пользователи ПК. Этот RC предназначен для доверенной локальной машины; порт нельзя открывать в сеть.

На Ubuntu Server обычные `codex` и `codex resume ID` в стандартном интерактивном режиме используют штатный общий daemon того же пользователя и `CODEX_HOME`. Rele не подменяет команду Codex и не меняет shell/profile. Явные `--no-daemon`, отдельный `--profile`, `--oss` и другие несовместимые с daemon параметры могут выбрать отдельное выполнение; CLI предупреждает об этом. Для строгого подключения без такого выбора остаётся `rele codex resume ID` с явным `--remote`. `codex exec` общий remote в проверяемых версиях не поддерживает.

В каталоге остаются исходные сохранённые чаты и ID. Общий server и native queue позволяют Desktop, CLI и Rele продолжать один контекст; ошибка не создаёт копию или fork. Потерянный ACK сверяется по исходному UUID без повторного enqueue. Windows native owner и общий endpoint сохраняются при обновлении Rele; Ubuntu поднимает daemon отдельным systemd starter/timer без GUI. [Установка и ограничения](docs/INSTALLATION.md).

**Выбранная интеграция Windows-установщика переводит старый недоступный локальный target в «Общий Codex» автоматически после проверки профиля и очереди.** Работающие, удалённые и защищённые отдельным ключом подключения сохраняются; их ручной переход выполняется при отсутствии активных запросов. Связки, токены и история сохраняются. Дополнительный «Сервер Rele» остаётся для отдельного owned процесса, который останавливается вместе с Rele.

Дополнительные режимы **proxy** и **WebSocket** присоединяются к уже работающему локальному app-server. Proxy не запускает чужой daemon при ошибке подключения. WebSocket принимает только loopback-адрес; токен вводится отдельно. Эти режимы полезны, если вы уже настроили общий живой сервер для нескольких клиентов. Пассивный Slack-контекст требует того же локального профиля и подтверждения записи в native истории. Подтверждения, обычные уточнения и отмена собственного запроса доступны из исходного мессенджера: `rele:cancel` в Slack, `/rele_cancel` в Telegram. На несколько вопросов отвечайте строками `1. ответ`, `2. ответ` по порядку.

## Связи и доступ

Назначение разговора Codex и доступ к запуску настраиваются в одной таблице; каждое значение сохраняется независимо для выбранного источника.

На странице **«Связи»** доступны вкладки **Telegram** и **Slack**. Таблица показывает все обнаруженные источники, включая несвязанные и личные чаты: группа/чат → тема/обсуждение → разговор Codex → доступ. Выберите существующий разговор в списке; несколько строк любой платформы могут использовать один Codex-тред с общей очередью и контекстом. Ответы, подтверждения и отмена остаются в исходном обсуждении.

**«Доступ»** в последней колонке задаётся для каждого входного треда:

| Режим | Действие |
| --- | --- |
| Выключено | Новые сообщения не запускают задачи и не передаются в Codex |
| По упоминанию | Полный контекст треда; запуск по свежему упоминанию подключённого агента |
| Все сообщения | Полный контекст; каждое разрешённое новое сообщение запускает задачу |

Новые источники выключены. В группах явно сохранённый режим разрешает участие всех авторов, включая других агентов; собственные ответы не запускаются повторно. В личных чатах выберите разрешённых людей; боты не допускаются. Существующие ограничения отправителей сохраняются до явного изменения и отмечаются в интерфейсе. Отключение одного источника не выключает остальные входы того же Codex.

В назначении доступно **«Создать при первом запросе…»**: укажите рабочую папку на компьютере Codex, затем отдельно включите доступ. Первый разрешённый запрос создаёт один новый native Codex-тред; соседние входные треды не получают это назначение. Правила автосоздания для будущих обсуждений целой группы и журнал операций находятся ниже таблицы на странице «Связи».

Смена назначения блокируется, пока источник имеет незавершённые запросы или автосоздание. При потерянном подтверждении создания можно выбрать существующий разговор и явно подтвердить продолжение сохранённых запросов; обычное изменение маршрута их не переносит. Ошибка или занятость Codex не создаёт запасной разговор.

Для обнаружения Slack откройте **«Найти источники»** и выберите чат и тред из каталога. Для Telegram отправьте `/rele_register` в нужном чате/теме. Каталог и регистрация не запускают Codex; старые игнорированные события не выполняются задним числом. Локальное название источника меняется в «Сведениях» и не переименовывает мессенджер или Codex.

Пауза общего Codex-разговора доступна в «Сведениях» и действует на все его входы. Уже выполняющийся запрос продолжает работу до завершения или отмены. Для принятого Slack-запроса выключенный источник сохраняет очередь и требует повторного включения для проверки полного контекста либо явной отмены. После включения доступная история треда может быть дозагружена целиком.

Схема SQLite v6 сохраняет данные и запрещает запуск старого бинарника, который не знает новые режимы доступа. Перед обновлением нужен штатный backup; откат — только с совместимой копией до миграции. [Эксплуатация](docs/OPERATIONS.md).

## Надёжность

- Входящее событие записывается в SQLite до подтверждения мессенджеру. Повтор не создаёт второй запрос.
- Постоянный UUID запроса сохраняется в `clientUserMessageId` Codex.
- `thread/queue/add` создаёт отдельный ход занятого треда. Rele не использует `turn/start` для отправки: этот метод может вмешаться в текущий ход.
- Потерянное подтверждение постановки вызывает сверку очереди и истории. Повтор `queue/add` с тем же UUID не идемпотентен и автоматически не выполняется.
- Финал и исходящие части ответа записываются одной транзакцией. Части доставляются по порядку.
- Явный отказ допускает повтор. Потерянное подтверждение отправки отображается как неопределённая доставка и автоматически не повторяется.
- Вмешательство Desktop в активный ход Rele блокирует внешнюю отправку смешанного ответа. Этот запрет сохраняется после перезапуска.

Прямые ходы Desktop / CLI не пересылаются в мессенджеры. Общий контекст включает обычное сжатие истории самим Codex. Маршрутизация ответа не создаёт изолированные контексты для Slack и Telegram.

## Голосовые

Аудио распознаётся локальным `faster-whisper`, в Codex отправляется текст. Модель устанавливается заранее; автоматическая загрузка при обработке сообщения запрещена. Функция выключена до настройки. Максимум 20 МиБ, до 10 минут обработки. [Установка и проверка](docs/VOICE.md).

## Данные и эксплуатация

- Windows: `%LOCALAPPDATA%\Rele`; секреты защищены DPAPI текущего пользователя.
- Ubuntu Server: `$XDG_STATE_HOME/rele` или `~/.local/state/rele`; каталог закрыт правами пользователя, конфигурация имеет режим `0600`.
- `RELE_DATA_DIR` задаёт каталог данных, `RELE_PORT` — loopback-порт.
- Ключ панели хранится в `sessionStorage` текущей вкладки и не передаётся в URL запросов API.

Штатные установщики управляют фоновым запуском. Остановка, резервные копии, переносимый режим и восстановление: [эксплуатация](docs/OPERATIONS.md).

## Разработка

Стандарт работы: [issue и критерии → scope выпуска → ветка/PR → проверки и пакеты → main и опубликованный RC → приёмка на windows-test-host/linux-test-host](docs/DEVELOPMENT.md). Windows собирается на windows-test-host, Linux — на linux-build-host, в изолированных каталогах. PR использует `Refs #…`, без автозакрытия issues; issue закрывается после принятия критериев. Обычные итерации выполняются в согласованных границах без нового разрешения на каждую правку; результаты привязываются к точным исходникам и пакетам. Приёмка готового приложения выполняется отдельно от source/dev-тестов. linux-test-host получает только готовые пакеты и узкие операторские скрипты, без исходников репозитория и dev-зависимостей.

Следующие команды относятся только к build/dev-этапу в изолированных каталогах windows-test-host/linux-build-host, не к приёмке установленного приложения и не к linux-test-host. Для них требуется Node.js **24.19.0** и npm:

```bash
npm ci
npm run typecheck
npm test
npm run build
npm start
```

Для разработки интерфейса запустите `npm run dev` и `npm run dev:web` в разных терминалах. Браузерные проверки:

```bash
npx playwright install chromium
npm run test:e2e
```

В build/dev-этапе `npm run probe:codex -- --help` описывает проверку каталога. `scripts/protocol-probe.py` проверяет общий внешний runtime; `scripts/managed-protocol-probe.py` — настоящий движок Rele, собственный дочерний процесс, передачу треда между процессами и адресные ответы. Оба используют отдельный тестовый профиль и локальный provider без пользовательских ключей. Автоматика и сборка выполняются в build-каталогах windows-test-host и linux-build-host. После PR/main и публикации RC на windows-test-host и linux-test-host проверяется готовое установленное приложение, без запуска dev-suite в этапе приёмки. Стабильный выпуск требует приёмки RC.

Архитектурные решения: [ARCHITECTURE.md](docs/ARCHITECTURE.md).


## GitHub Actions

GitHub Actions исключён из рабочего процесса из-за бесплатного лимита: ручные dispatch/rerun и автоматические запуски не выполняются. Автопроверки и сборка выполняются в изолированных build-каталогах windows-test-host и linux-build-host; наличие workflow-файла не означает разрешения его запускать. Обязательные проверки обеих ОС, отдельная приёмка готового приложения на windows-test-host/linux-test-host и привязка опубликованного RC к проверенным байтам сохраняются. [Стандарт разработки](docs/DEVELOPMENT.md), [критерии приёмки](docs/ACCEPTANCE.md).
