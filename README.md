# Rele

Локальное приложение, которое связывает Telegram и Slack с общими разговорами Codex. Контекст хранит Codex; ответ и запрос подтверждения возвращаются в источник конкретного запроса.

## Целевой сценарий

- Windows: Rele, codex app-server и Codex Desktop на одном ПК.
- Ubuntu Server: Rele, codex app-server и Codex CLI на одном сервере.
- Один разговор Codex: несколько источников Telegram и тредов Slack.
- Общий контекст Codex; каждый ответ возвращается в источник своего запроса.
- Веб-панель показывает связи по названиям.

WSL и отдельный компонент Rele Node исключены из первого релиза.

## Установка

Инструкция описывает установку фактических файлов из GitHub Release. Она не
публикует и не создаёт пакет. Пока на странице Releases нет файлов, установить

## Подключение Codex

В режиме **«Общий Codex»** доступны два варианта выбора:

- **«Максимальная поддерживаемая версия»** — самая новая из найденных установленных версий, поддерживаемых Rele. Более новая неподдерживаемая версия не вытесняет поддерживаемую.
- **«Выбрать конкретную версию»** — выбранный исполняемый файл; Rele сохраняет этот выбор и не заменяет его автоматически.

Оба варианта используют исходный профиль Codex. Windows сохраняет необходимые файлы выбранного native runtime в рабочую копию Rele и запускает её native backend на постоянном адресе `ws://127.0.0.1:PORT`; отдельный CLI не требуется. Обновление Desktop не удаляет файлы этой рабочей копии. Ubuntu Server использует штатный daemon установленного CLI и его UDS. Сохранение выбора версии не заменяет работающий подтверждённый общий сервер и не меняет подключение Desktop.

Страница Codex показывает работающую и выбранную версии отдельно. На Windows нажмите **«Подготовить обновление»**: Rele подготовит следующий запуск на выбранной поддерживаемой версии, а текущий сервер и работающие задачи продолжат работу. Автоматический режим выбирает максимальную поддерживаемую версию; ручной использует только выбранный файл. Понижение версии общего сервера пока блокируется: совместимость нового профиля со старым backend не подтверждена. Обновление Rele и «Обновить статус» сами по себе сервер не заменяют. Сменить выбор можно после завершения незаконченных операций Rele; уже подготовленное обновление нужно сначала завершить.

Для применения завершите задачи и полностью выйдите из Codex Desktop, CLI и остальных клиентов общего сервера. Отметьте **«Я завершил задачи и полностью закрыл Codex Desktop и CLI»** и нажмите **«Обновить Codex»**. Клиенты должны оставаться закрытыми до завершения операции. Rele приостанавливает отправку своей очереди, проверяет общий простой и отсутствие других подключений, останавливает только проверенный собственный экземпляр задачи Codex и запускает подготовленную версию с прежними адресом и профилем. После проверки нового сервера Rele переподключается и продолжает очередь; новые входящие запросы сохраняются во время паузы. Дождитесь подтверждения и откройте Desktop обычным способом. Перезагрузка Windows и UAC не требуются; Rele не закрывает внешние клиенты принудительно.

«Desktop: подключение настроено» означает сохранённую настройку запуска, а не проверку текущего окна Desktop. Параметры сервера доступны в «Настройки подключения», пути и адрес — в «Технические сведения».

Пустое поле профиля наследует `CODEX_HOME` окружения либо стандартный `~/.codex` владельца Rele. Для нестандартного Desktop-профиля укажите тот же полный путь. Панель показывает фактический профиль; авторизация и настройки остаются в Codex, Rele не переписывает `config.toml`.

На Windows установщик по умолчанию подключает обычный запуск Codex Desktop к общему серверу. Один раз полностью выйдите из уже работающего Desktop и откройте его обычным способом. Выбор интеграции сохраняется при обновлении Rele; ранее отключённая интеграция и конфликтующие чужие настройки не заменяются молча. Дополнительный пункт «Codex Desktop (общий с Rele)» остаётся для явного запуска с нужным окружением.

Если подключение Desktop было пропущено, после сохранения «Общий Codex» явно нажмите «Подключить обычный Codex Desktop» в разделе «Codex». Там же можно отключить интеграцию перед сменой сервера или профиля. Эти действия не закрывают работающие окна, не останавливают Rele и не заменяют выбранный профиль. Статус показывает настройки установки; фактическое подключение уже открытого Desktop проверяется отдельно.

Desktop обращается к серверу напрямую: установщик задаёт только пользовательский `CODEX_APP_SERVER_WS_URL`. Прежние принадлежащие Rele `CODEX_CLI_PATH`/`CODEX_APP_SERVER_FORCE_CLI` восстанавливаются по сохранённым значениям; чужие изменения сохраняются. Общие инструменты и настройки берутся из исходного профиля. Windows-сервер слушает только `127.0.0.1` без токена: к нему могут подключаться другие локальные процессы и пользователи ПК. Этот RC предназначен для доверенной локальной машины; порт нельзя открывать в сеть.

На Ubuntu Server обычные `codex` и `codex resume ID` в стандартном интерактивном режиме используют штатный общий daemon того же пользователя и `CODEX_HOME`. Rele не подменяет команду Codex и не меняет shell/profile. Явные `--no-daemon`, отдельный `--profile`, `--oss` и другие несовместимые с daemon параметры могут выбрать отдельное выполнение; CLI предупреждает об этом. Для строгого подключения без такого выбора остаётся `rele codex resume ID` с явным `--remote`. `codex exec` общий remote в проверяемых версиях не поддерживает.

В каталоге остаются исходные сохранённые чаты и ID. Общий server и native queue позволяют Desktop, CLI и Rele продолжать один контекст; ошибка не создаёт копию или fork. Потерянный ACK сверяется по исходному UUID без повторного enqueue. Windows native owner и общий endpoint сохраняются при обновлении Rele; Ubuntu поднимает daemon отдельным systemd starter/timer без GUI. [Установка и ограничения](docs/INSTALLATION.md).

**Выбранная интеграция Windows-установщика переводит старый недоступный локальный target в «Общий Codex» автоматически после проверки профиля и очереди.** Работающие, удалённые и защищённые отдельным ключом подключения сохраняются; их ручной переход выполняется при отсутствии активных запросов. Связки, токены и история сохраняются. Дополнительный «Сервер Rele» остаётся для отдельного owned процесса, который останавливается вместе с Rele.

Дополнительные режимы **proxy** и **WebSocket** присоединяются к уже работающему локальному app-server. Proxy не запускает чужой daemon при ошибке подключения. WebSocket принимает только loopback-адрес; токен вводится отдельно. Эти режимы полезны, если вы уже настроили общий живой сервер для нескольких клиентов. Пассивный Slack-контекст требует того же локального профиля и подтверждения записи в native истории. Подтверждения, обычные уточнения и отмена собственного запроса доступны из исходного мессенджера: `rele:cancel` в Slack, `/rele_cancel` в Telegram. На несколько вопросов отвечайте строками `1. ответ`, `2. ответ` по порядку.

## Связи и доступ

Назначение разговора Codex и доступ к запуску настраиваются в одной таблице; каждое значение сохраняется независимо для выбранного источника.

На странице **«Связи»** доступны вкладки **Telegram** и **Slack**. Таблица показывает все обнаруженные источники, включая несвязанные и личные чаты: группа/чат → тема/обсуждение → разговор Codex → доступ. Выберите существующий разговор в списке; несколько строк любой платформы могут использовать один Codex-тред с общей очередью и контекстом. Ответы, подтверждения и отмена остаются в исходном обсуждении.

**«Доступ»** в последней колонке задаётся для каждого входного треда:

| Режим | Действие |
| --- | --- |
| Выключено | Новые сообщения не запускают задачи и не передаются в Codex |
| По упоминанию | Полный контекст треда; запуск по свежему упоминанию подключённого агента |
| Все сообщения | Полный контекст; каждое разрешённое новое сообщение запускает задачу |

Новые источники выключены. В группах явно сохранённый режим разрешает участие всех авторов, включая других агентов; собственные ответы не запускаются повторно. В личных чатах выберите разрешённых людей; боты не допускаются. Существующие ограничения отправителей сохраняются до явного изменения и отмечаются в интерфейсе. Отключение одного источника не выключает остальные входы того же Codex.

В назначении доступно **«Создать при первом запросе…»**: укажите рабочую папку на компьютере Codex, затем отдельно включите доступ. Первый разрешённый запрос создаёт один новый native Codex-тред; соседние входные треды не получают это назначение. Правила автосоздания для будущих обсуждений целой группы и журнал операций находятся ниже таблицы на странице «Связи».

Смена назначения блокируется, пока источник имеет незавершённые запросы или автосоздание. При потерянном подтверждении создания можно выбрать существующий разговор и явно подтвердить продолжение сохранённых запросов; обычное изменение маршрута их не переносит. Ошибка или занятость Codex не создаёт запасной разговор.

Для обнаружения Slack откройте **«Найти источники»** и выберите чат и тред из каталога. Для Telegram отправьте `/rele_register` в нужном чате/теме. Каталог и регистрация не запускают Codex; старые игнорированные события не выполняются задним числом. Локальное название источника меняется в «Сведениях» и не переименовывает мессенджер или Codex.

Пауза общего Codex-разговора доступна в «Сведениях» и действует на все его входы. Уже выполняющийся запрос продолжает работу до завершения или отмены. Для принятого Slack-запроса выключенный источник сохраняет очередь и требует повторного включения для проверки полного контекста либо явной отмены. После включения доступная история треда может быть дозагружена целиком.

Схема SQLite v6 сохраняет данные и запрещает запуск старого бинарника, который не знает новые режимы доступа. Перед обновлением нужен штатный backup; откат — только с совместимой копией до миграции. [Эксплуатация](docs/OPERATIONS.md).

## Надёжность

- Входящее событие записывается в SQLite до подтверждения мессенджеру. Повтор не создаёт второй запрос.
- Постоянный UUID запроса сохраняется в `clientUserMessageId` Codex.
- `thread/queue/add` создаёт отдельный ход занятого треда. Rele не использует `turn/start` для отправки: этот метод может вмешаться в текущий ход.
- Потерянное подтверждение постановки вызывает сверку очереди и истории. Повтор `queue/add` с тем же UUID не идемпотентен и автоматически не выполняется.
- Финал и исходящие части ответа записываются одной транзакцией. Части доставляются по порядку.
- Явный отказ допускает повтор. Потерянное подтверждение отправки отображается как неопределённая доставка и автоматически не повторяется.
- Вмешательство Desktop в активный ход Rele блокирует внешнюю отправку смешанного ответа. Этот запрет сохраняется после перезапуска.

Прямые ходы Desktop / CLI не пересылаются в мессенджеры. Общий контекст включает обычное сжатие истории самим Codex. Маршрутизация ответа не создаёт изолированные контексты для Slack и Telegram.

## Голосовые

Аудио распознаётся локальным `faster-whisper`, в Codex отправляется текст. Модель устанавливается заранее; автоматическая загрузка при обработке сообщения запрещена. Функция выключена до настройки. Максимум 20 МиБ, до 10 минут обработки. [Установка и проверка](docs/VOICE.md).

## Данные и эксплуатация

- Windows: `%LOCALAPPDATA%\Rele`; секреты защищены DPAPI текущего пользователя.
- Ubuntu Server: `$XDG_STATE_HOME/rele` или `~/.local/state/rele`; каталог закрыт правами пользователя, конфигурация имеет режим `0600`.
- `RELE_DATA_DIR` задаёт каталог данных, `RELE_PORT` — loopback-порт.
- Ключ панели хранится в `sessionStorage` текущей вкладки и не передаётся в URL запросов API.

Штатные установщики управляют фоновым запуском. Остановка, резервные копии, переносимый режим и восстановление: [эксплуатация](docs/OPERATIONS.md).

## Разработка

Стандарт работы: [issue и критерии → scope → ветка/PR → GitHub Actions → draft RC → приёмка готового пакета](docs/DEVELOPMENT.md). Draft PR запускает быстрые проверки на Ubuntu и Windows; ready PR и `main` запускают полный набор и сборку пакетов на тех же двух GitHub-hosted runner-ах. Обычные PR/main-проверки не загружают workflow artifacts. Ручной release dispatch из `main` запускает один workflow run: параллельные Ubuntu и Windows jobs загружают проверенные пакеты в один непубликованный draft Release, а publisher скачивает и проверяет их оттуда. Actions Artifacts и кэш не используются; отдельная квота Actions artifact storage не нужна. Приёмка опубликованного пакета остаётся отдельной проверкой на Windows и Linux acceptance host. Issue закрывается только после принятия его критериев.

GitHub Actions выполняет автоматические проверки проекта. Следующие команды оставлены для локальной разработки и точечной диагностики; это не отдельный release-build маршрут. Для них требуется Node.js **24.19.0** и npm:

```bash
npm ci
npm run typecheck
npm test
npm run build
npm start
```

Для разработки интерфейса запустите `npm run dev` и `npm run dev:web` в разных терминалах. Браузерные проверки:

```bash
npx playwright install chromium
npm run test:e2e
```

`scripts/protocol-probe.py` и `scripts/managed-protocol-probe.py` используют отдельный тестовый профиль и локальный provider без пользовательских ключей; CI запускает их на hosted runners. После публикации RC Windows и Linux acceptance host проверяют готовые пакеты без исходников и dev-suite. Stable выпускается только после приёмки RC.

Архитектурные решения: [ARCHITECTURE.md](docs/ARCHITECTURE.md).


## GitHub Actions

GitHub Actions проверяет PR и `main` на стандартных Windows/Linux runners; draft PR получает быстрый набор, ready PR и `main` — полный, включая сборку пакетов. Workflow не использует npm cache и не загружает artifacts в обычных PR/main runs. Только ручной release dispatch из `main` создаёт непубликованный draft RC, принимает проверенные пакеты от двух OS jobs через assets этого Release и проверяет их на publisher-е. Actions Artifacts и кэш не используются. См. [схему CI](docs/CI.md) и [стандарт разработки](docs/DEVELOPMENT.md).
