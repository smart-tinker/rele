# Приёмка стабильного выпуска

Release candidate допускает оценку и тестовую эксплуатацию. Стабильный v0.1.0 требует выполнения нижеприведённых сценариев в реальных разрешённых средах.

## Доказательства автоматических проверок

Автоматические проверки каждого выпуска должны пройти на Windows и Ubuntu. Их можно выполнить на выделенных локальных стендах теми же scripts; GitHub Actions не является обязательным местом запуска. В доказательствах связываются точный commit, версии инструментов и хеши проверенных пакетов. Во время разработки сначала выполняется узкая проверка изменённого участка. Полная матрица запускается один раз для итогового состояния; повтор нужен только после нового diff, ошибки или изменения среды. GitHub workflow запускается только вручную и не расходует минуты на каждый PR/push. Полный ручной запуск на main публикует RC из своих проверенных артефактов без второй пересборки. В нём проверяются типизация, SQLite, восстановление, корреляция, права панели, адаптеры, настоящий Codex protocol fixture с локальным mock provider, браузерные сценарии, вход через одноразовую ссылку в production-сборке, распакованные архивы и настоящие Windows / Debian установщики (установка, перезапуск, обновление, backup, удаление с сохранением данных).

Точная allowlist Codex: 0.163.0, 0.163.0-alpha.10.2, 0.163.0-alpha.11, 0.163.0-alpha.11.2, 0.164.0-alpha.11.1, 0.165.0-alpha.1.2 и 0.166.0-alpha.5.1. Результаты проверки конкретного commit и каждой ОС фиксируются в release notes; наличие pin не означает повтор полного набора проверок для каждого выпуска. Для установленного Desktop результаты backend и обычного запуска GUI фиксируются отдельно; протокольный PASS не заменяет GUI-приёмку. Отдельный managed fixture запускает настоящий Engine, SQLite и CodexClient Rele: два независимых процесса Codex передают исходный тред, проверяются название, контекст, ожидание чужого writer, освобождение треда, адресная доставка и остановка дочернего процесса. Внешний runtime fixture сохраняет проверку очереди, подтверждений, mixed-turn и потерянного ACK.

Протокольные проверки не используют пользовательские ключи и не доказывают поведение окна установленного Windows Desktop. Тесты адаптеров не отправляют сообщения в настоящий Slack / Telegram.

## Windows Desktop

- [ ] Записать точные версии Windows, Desktop, CLI и подключённого app-server.
- [ ] Установить Rele с default-интеграцией под пользователем Desktop: исходный профиль, прямой WS, только адрес подключения Desktop. Ручной выбор режима или подключение в панели не требуется.
- [ ] Выбрать существующий тред Desktop по имени и рабочему каталогу; подтвердить исходный threadId без нового чата или fork.
- [ ] Запрос Telegram виден в общей истории Desktop; ответ получает только Telegram.
- [ ] Продолжение из Slack учитывает прежний обмен; ответ получает только Slack.
- [ ] Прямой Desktop запрос не пересылается ни в один мессенджер.
- [ ] Пока Desktop удерживает тред, Rele сохраняет запрос queued с понятным ожиданием и не начинает второй writer.
- [ ] Зафиксировать, как конкретный Desktop освобождает тред: закрытие чата / окна / завершение процесса. После этого исходный запрос Rele выполняется один раз с прежней историей.
- [ ] После завершения Rele другой клиент возобновляет тот же ID и видит новый контекст; записать, требуется ли переоткрытие чата для обновления UI.
- [ ] Для дополнительного режима общего внешнего runtime вмешательство Desktop в выполняющийся Rele turn блокирует смешанный внешний ответ.
- [ ] Подтверждение от Desktop и подтверждение Rele не отвечают на чужой RPC.
- [ ] При общем app-server Desktop остаётся открытым: подтверждение, несколько длинных вопросов и отмена из исходного Slack/Telegram выполняются с телефона без действий на ноутбуке.
- [ ] Потеря ACK пассивного контекста сверяется по точному native receipt; гонка с запуском и отменой хода не теряет сообщение.
- [ ] Закрытый Desktop не мешает работе собственного сервера Rele; повторное открытие не дублирует запрос и не подменяет тред.
- [ ] Проверить установленный Rele, автозапуск задачи и DPAPI после выхода / входа текущего пользователя.
- [ ] Поиск при открытом и закрытом Desktop показывает правильный backend, включая версионированный bin; поиск не запускает GUI или app-server, сохранение managed-настроек запускает только собственный сервер Rele.
- [ ] Установка, обновление и удаление через обычный интерактивный интерфейс работают под обычным пользователем Windows.

Если выбранный runtime отличается от трёх проверенных версий, сначала требуется отдельная проверка нового протокола и обновление адаптера. Отключать проверку версии для прохождения приёмки нельзя.

## Общий native daemon и восстановление

Shared fixture использует реальные Codex и Engine с локальным fake provider: общий PID/профиль/ID, Windows direct WS peer или Ubuntu native daemon, потерянный queue ACK, restart без resend, исходный контекст, cross-client approvals/questions/cancel, own shell cleanup и wrong-profile fence. Windows installer gate проверяет независимый owner через restart/upgrade/uninstall; Linux — native PID вне rele.service cgroup. Эти проверки не заменяют настоящий Desktop GUI, реальные мессенджеры и reboot приёмку.

- [ ] Windows: после перезагрузки и входа Rele находит/поднимает общий Codex, продолжает прежний чат; последующий запуск Desktop присоединяется к тому же серверу.
- [ ] Ubuntu Server: после reboot без GUI/user D-Bus daemon восстанавливается, интерактивный CLI и Rele открывают прежние ID.
- [ ] Открытый настоящий Desktop остаётся подключённым после обновления Rele; native PID и адрес сохранены, адаптер отсутствует, активная задача и управление из телефона сохраняются.
- [ ] Переход со старого приватного Desktop требует одного Quit; конфликт чужого окружения понятен, чужие процессы/настройки не изменяются.
- [ ] После Stop единственный подтверждённый собственный native queue item продолжается автоматически; чужая/смешанная очередь не запускается. Неопределённый ACK сверяется по UUID без повтора.

## Ubuntu Server и мессенджеры

- [ ] CLI и сервер Rele под владельцем Codex используют один настоящий профиль и по очереди продолжают исходный тред без Desktop.
- [ ] Telegram: личный чат и нужная forum topic, корректные названия и локальные подписи.
- [ ] Slack: нужный workspace, канал, корневой тред и отображение имён.
- [ ] Обе платформы продолжают контекст одного треда и получают только свои ответы.
- [ ] Посторонний отправитель не запускает задачи и не подтверждает чужую.
- [ ] Смена связки при выполняющемся запросе не перенаправляет его ответ.
- [ ] Два одновременных запроса сохраняют отдельные ходы и правильные origin.
- [ ] Повтор доставки входящего события не дублирует работу.
- [ ] Отказ / ограничение частоты и потеря ACK правильно различаются.
- [ ] Перезапуск Rele между постановкой, завершением и отправкой не запускает задачу заново.
- [ ] Длинный ответ доставляется частями в исходную тему по порядку.
- [ ] Подтверждение команды, записи файлов и уточнение вопроса проходят в предназначенном источнике.
- [ ] Голосовое в нужном языке распознаётся локально на обеих целевых машинах.
- [ ] Служба systemd пакета под владельцем Codex переживает сетевой обрыв и перезагрузку Ubuntu; backup восстанавливает связки.
- [ ] Нет plaintext tokens в API, URL, логах диагностики и release artifacts.

## Slack rich-ответы и контекст

- [ ] При выполнении и распознавании аудио Agent Session получает `processing`; при вопросе или подтверждении — `suspended`; очередь, подготовка, неопределённость и завершение дают `active`. После доставки ответа статус не остаётся ложным Working.
- [ ] Отдельно проверить spinner в обычных Activity/Threads и сравнить с индикатором внутри треда. Точный вид и замена галочки прочтения в списке пока не подтверждены.
- [ ] Жирный текст, заголовки, списки, код, ссылки и таблицы отображаются как rich-содержимое; локальные Codex citation directives не видны как сырой синтаксис.
- [ ] Сообщения всех людей и агентов, включая неразрешённых отправителей и Rele, видны в журнале и учитываются следующим запросом модели без самостоятельного ответа на пассивную реплику.
- [ ] Отмеченный другой бот со свежим упоминанием подключённого Slack-агента запускает задачу; тот же бот без упоминания, цитата/код, правка и собственный ответ Rele её не запускают.
- [ ] Тред длиннее одной страницы догружается полностью; перезапуск и обрыв Slack не пропускают backlog. До конца загрузки новый запрос ждёт.
- [ ] Проверить наблюдённые правку/удаление, blocks-only сообщение и metadata файла; API-невидимые удаления/retention и байты вложений не объявляются восстановленными.
- [ ] Во время занятого Desktop контекст остаётся pending; после освобождения попадает в исходный Codex ID. Пассивные реплики доступны модели, отдельные bubbles Desktop для них не требуются.
- [ ] При миграции rc.5 → rc.6 сохраняются связки, ACL, очередь и история; для отката используется backup v3.

## Slack Agent Sessions и Stop rc.8

- [ ] Новая Slack app из manifest объявлена через `agent_view`, имеет выданные `assistant:write` и `chat:write` и подписку `agent_session_stopped`. При обновлении существующей app сохранены прежние scopes/events и включённый `assistant_view`; необратимая миграция на `agent_view` не выполнялась автоматически. Новые scopes прошли явную переавторизацию без передачи токенов в чат.
- [ ] Без подписки Stop появляется понятная диагностика настройки, обычная задача продолжает выполняться. Одно обновление Rele не объявляется достаточным для настройки Slack app.
- [ ] Штатный Stop в исходном треде от исходного отправителя останавливает только его запрос, с receipt до native действия и подтверждённым итогом после сверки. Другой автор, account, channel или thread не получают права отмены.
- [ ] Повтор Stop, в том числе после перезапуска, не повторяет отмену; запоздавшее событие не создаёт новую задачу, не попадает в транскрипт и не отменяет более поздний или локально queued запрос.
- [ ] Stop смешанного с другим клиентом хода не выполняет native interrupt/delete. Команды `rele:cancel` и `/rele_cancel` сохраняют прежние origin-проверки и возможность отменить ожидающий запрос.

Живая проверка rc.8 на рабочем Windows, штатной кнопки Stop и управления с телефона остаётся открытой до отдельного фактического прогона. Автоматические тесты не подтверждают внешний вид Slack client.

## Desktop-only bootstrap (rc.14)

- На disposable Windows установленная официальная Desktop-поставка обнаруживается автоматически без npm CLI и готового native package. Rele запускает общий сервер в исходном профиле.
- До запуска сохраняется обычный Codex-тред с историей; после подключения виден тот же ID и контекст. Restart/восстановление сохраняют thread/request UUID и управление из исходного мессенджера.
- Готовый daemon не заменяется; приватный/неизвестный owner, неподдерживаемая версия, неполная поставка, изменение источника и повреждение кэша блокируются.
- Файлы разных Desktop-поставок не смешиваются, ссылки за пределы bundle не допускаются. Кэш публикуется атомарно; native selection/auth/history Rele вручную не записывает.
- Итоговый commit проходит полную Windows/Ubuntu матрицу, три native pins и installer/recovery/SID/ACL/DPAPI. Backend из настоящего MSIX и stdio shim не заменяют отдельную приёмку настоящего GUI.
