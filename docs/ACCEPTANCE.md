# Приёмка стабильного выпуска

Release candidate допускает оценку и тестовую эксплуатацию. Стабильный v0.1.0 требует выполнения нижеприведённых сценариев в реальных разрешённых средах.

## Доказательства автоматических проверок

CI каждого выпуска должен быть зелёным на Windows и Ubuntu. В нём проверяются типизация, SQLite, восстановление, корреляция, права панели, адаптеры, настоящий Codex protocol fixture с локальным mock provider, браузерные сценарии, вход через одноразовую ссылку в production-сборке, распакованные архивы и настоящие Windows / Debian установщики (установка, перезапуск, обновление, backup, удаление с сохранением данных).

CI проверяет точные версии Codex 0.163.0 и 0.163.0-alpha.10.2 на обеих ОС. Отдельный managed fixture запускает настоящий Engine, SQLite и CodexClient Rele: два независимых процесса Codex передают исходный тред, проверяются название, контекст, ожидание чужого writer, освобождение треда, адресная доставка и остановка дочернего процесса. Внешний runtime fixture сохраняет проверку очереди, подтверждений, mixed-turn и потерянного ACK.

Протокольные проверки не используют пользовательские ключи и не доказывают поведение окна установленного Windows Desktop. Тесты адаптеров не отправляют сообщения в настоящий Slack / Telegram.

## Windows Desktop

- [ ] Записать точные версии Windows, Desktop, CLI и подключённого app-server.
- [ ] Выбрать «Сервер Rele» под тем же пользователем и указать тот же фактический профиль Codex, что у Desktop.
- [ ] Выбрать существующий тред Desktop по имени и рабочему каталогу; подтвердить исходный threadId без нового чата или fork.
- [ ] Запрос Telegram виден в общей истории Desktop; ответ получает только Telegram.
- [ ] Продолжение из Slack учитывает прежний обмен; ответ получает только Slack.
- [ ] Прямой Desktop запрос не пересылается ни в один мессенджер.
- [ ] Пока Desktop удерживает тред, Rele сохраняет запрос queued с понятным ожиданием и не начинает второй writer.
- [ ] Зафиксировать, как конкретный Desktop освобождает тред: закрытие чата / окна / завершение процесса. После этого исходный запрос Rele выполняется один раз с прежней историей.
- [ ] После завершения Rele другой клиент возобновляет тот же ID и видит новый контекст; записать, требуется ли переоткрытие чата для обновления UI.
- [ ] Для дополнительного режима общего внешнего runtime вмешательство Desktop в выполняющийся Rele turn блокирует смешанный внешний ответ.
- [ ] Подтверждение от Desktop и подтверждение Rele не отвечают на чужой RPC.
- [ ] При общем app-server Desktop остаётся открытым: подтверждение, несколько длинных вопросов и отмена из исходного Slack/Telegram выполняются с телефона без действий на ноутбуке.
- [ ] Потеря ACK пассивного контекста сверяется по точному native receipt; гонка с запуском и отменой хода не теряет сообщение.
- [ ] Закрытый Desktop не мешает работе собственного сервера Rele; повторное открытие не дублирует запрос и не подменяет тред.
- [ ] Проверить установленный Rele, автозапуск задачи и DPAPI после выхода / входа текущего пользователя.
- [ ] Поиск при открытом и закрытом Desktop показывает правильный backend, включая версионированный bin; поиск не запускает GUI или app-server, сохранение managed-настроек запускает только собственный сервер Rele.
- [ ] Установка, обновление и удаление через обычный интерактивный интерфейс работают под обычным пользователем Windows.

Если выбранный runtime отличается от двух проверенных версий, сначала требуется отдельная проверка нового протокола и обновление адаптера. Отключать проверку версии для прохождения приёмки нельзя.

## Ubuntu Server и мессенджеры

- [ ] CLI и сервер Rele под владельцем Codex используют один настоящий профиль и по очереди продолжают исходный тред без Desktop.
- [ ] Telegram: личный чат и нужная forum topic, корректные названия и локальные подписи.
- [ ] Slack: нужный workspace, канал, корневой тред и отображение имён.
- [ ] Обе платформы продолжают контекст одного треда и получают только свои ответы.
- [ ] Посторонний отправитель не запускает задачи и не подтверждает чужую.
- [ ] Смена связки при выполняющемся запросе не перенаправляет его ответ.
- [ ] Два одновременных запроса сохраняют отдельные ходы и правильные origin.
- [ ] Повтор доставки входящего события не дублирует работу.
- [ ] Отказ / ограничение частоты и потеря ACK правильно различаются.
- [ ] Перезапуск Rele между постановкой, завершением и отправкой не запускает задачу заново.
- [ ] Длинный ответ доставляется частями в исходную тему по порядку.
- [ ] Подтверждение команды, записи файлов и уточнение вопроса проходят в предназначенном источнике.
- [ ] Голосовое в нужном языке распознаётся локально на обеих целевых машинах.
- [ ] Служба systemd пакета под владельцем Codex переживает сетевой обрыв и перезагрузку Ubuntu; backup восстанавливает связки.
- [ ] Нет plaintext tokens в API, URL, логах диагностики и release artifacts.

## Slack rich-ответы и контекст rc.6

- [ ] Во время подтверждённого выполнения или распознавания аудио появляется штатный индикатор под полем ввода Slack. Очередь, подготовка к запуску и ожидание подтверждения очищают его; после подтверждения выполнение снова показывает статус.
- [ ] Отдельно проверить желаемый индикатор в списке Threads: текущий API управляет статусом под полем ввода; замена галочки прочтения в списке не подтверждена.
- [ ] Жирный текст, заголовки, списки, код, ссылки и таблицы отображаются как rich-содержимое; локальные Codex citation directives не видны как сырой синтаксис.
- [ ] Сообщения всех людей и агентов, включая неразрешённых отправителей и Rele, видны в журнале и учитываются следующим запросом модели без самостоятельного ответа на пассивную реплику.
- [ ] Отмеченный другой бот со свежим @Rele запускает задачу; тот же бот без упоминания, цитата/код, правка и собственный ответ Rele её не запускают.
- [ ] Тред длиннее одной страницы догружается полностью; перезапуск и обрыв Slack не пропускают backlog. До конца загрузки новый запрос ждёт.
- [ ] Проверить наблюдённые правку/удаление, blocks-only сообщение и metadata файла; API-невидимые удаления/retention и байты вложений не объявляются восстановленными.
- [ ] Во время занятого Desktop контекст остаётся pending; после освобождения попадает в исходный Codex ID. Пассивные реплики доступны модели, отдельные bubbles Desktop для них не требуются.
- [ ] При миграции rc.5 → rc.6 сохраняются связки, ACL, очередь и история; для отката используется backup v3.

## Запись результата

Для каждой машины сохраните дату, версию Rele, commit/tag, версии Codex, перечень пройденных сценариев и найденные отклонения. Не включайте токены, частную историю и служебные файлы с учётными данными в публичные отчёты.

Условия остаются открытыми, пока нет фактического прогона. Автоматическая смена prerelease на stable запрещена. Связанные задачи: issue #1 и issue #2.
