# Ход работы, вопросы и результат в Slack

Rele накапливает публичные комментарии Codex и план внутри текущего этапа.
Новый комментарий не заменяет предыдущий. Перед вопросом этап сохраняется и
закрывается для последующих комментариев; вопрос публикуется отдельной
карточкой после него. Разрешённый ввод своего запроса и подтверждённый ответ
на свой вопрос также сохраняют границу. Следующий публичный комментарий или
план создаёт новый блок на своём месте. Пустые блоки не публикуются.

Обычный порядок: ход работы → вопрос → ответ человека → следующий ход работы
→ отдельный новый итог. У этапов, маркера ответа и итога свои Slack message ID
и receipts. Завершённый этап показывает «Этап завершён»; будущий итог в него
не добавляется. Повторы Codex обновляют текущий блок. Уже доставленный старый
итог с прежним общим receipt повторно не публикуется.

Async-вопрос может остаться открытым после завершения исходного хода: его
ожидание само по себе не задерживает итог. Поздний ответ создаёт штатное
продолжение с новым ходом работы и итогом ниже ответа; старый итог остаётся
на месте.

## Вопрос и ответ

До ответа доступны существующие кнопки и форма. После закрытия карточка
показывает короткий текст сохранённого вопроса (заголовок — только fallback), фактический ответ,
известного автора или источник и точный статус. Длинный ответ отмечен как
фрагмент; его точная строка сохраняется в подробностях. Исходный вопрос,
варианты и история доступны через штатные раскрываемые `task_card.details`
«Подробнее о вопросе», без input, submit, нового запроса или native RPC.
Дополнительные части прежнего сообщения показывают статус и отсылку к
первой части; старое приглашение ответить в них не остаётся.

Текстовый ответ уже имеет собственное сообщение человека в Slack. Для
короткой кнопки или отправленной формы Rele сохраняет отдельный маркер в
durable outbox до отправки. Открытие формы и невалидный callback маркер не
создают. Маркер показывает получение ответа и затем текущий статус, без
повтора полного вопроса и ответа. Продолжение не обгоняет его доставку;
предшествующие сообщения исходного запроса сохраняют свой порядок.

«Ответ ожидает отправки», «Ответ отправляется» и «Результат отправки ответа
неизвестен» не означают подтверждённую отправку в Codex. Отправка ответа не
означает приёмку результата всей задачи. Подтверждённый typed async-ответ из
native истории показывает точную строку и источник Codex, без выдуманного
автора. При одном `serverRequest/resolved` без доказанного точного ответа
показывается только «Вопрос закрыт в Codex». Секретные ответы и значения при
неопределённом результате отправки не публикуются. Обновление известной
карточки или маркера не повторяет
ответ, input или RPC.

## Подробности и форматирование

Длинный ход работы разбивается на страницы по 6000 символов в подробностях
своего этапа. Кнопки «Назад» и «Далее» привязаны к этому этапу и его исходному
сообщению; по умолчанию показывается последняя страница. Длинный отдельный
итог использует подготовленные части ответа, начиная с первой. Перелистывание
меняет это сообщение для всех участников треда, не запускает Codex и не
считается ответом на вопрос. Выбранная страница сохраняется в Rele.

Подробности закрытого вопроса используют несколько штатных раскрываемых
карточек при необходимости. Для истории за пределами лимита блоков Slack
явно указано продолжение в Codex; сохранённые вопросы и ответы не удаляются.

Итог сохраняет Markdown, таблицы, ссылки и читаемые ссылки Codex. Внутренние
`codex-annotation` вне inline/fenced code удаляются целиком, без утечки
атрибутов вроде `index="1"`. Буквальные примеры в коде и обычный текст с таким
атрибутом сохраняются. Исходная история Codex не переписывается.

## Доставка, восстановление и границы

Границы и принадлежность известных комментариев этапам сохраняются в Rele.
История того же запроса восстанавливает порядок только при наличии
подтверждённого чередования публичных событий; неизвестный старый порядок
не выдумывается. Повтор события не дублирует комментарий, закрытые этапы не
принимают поздние события. Пассивные реплики, импорт, собственные/bot echoes
и открытие формы сами по себе не создают этап.

До первой отправки этапа, маркера или итога сохраняется intent. Известный
message ID позволяет безопасно повторить замену содержимого через
`chat.update`. Потерянный ACK первой отправки остаётся неопределённым и не
ведёт к слепому повтору `postMessage`. Итог использует отдельный durable
outbox/receipt, поэтому неопределённая первая отправка прогресса не заставляет
добавлять результат в старую карточку. Совместимость учитывает прежний
доставленный итог только с совпавшими origin и содержимым. Старые сообщения
массово не удаляются и не перепубликуются.

Публикуются только публичные `agentMessage` с фазой `commentary` и план.
Скрытые рассуждения, аргументы инструментов и вывод команд не передаются.
Чужие ходы и смешанный ввод Desktop/Rele блокируют экспорт непроверенного
результата; известные карточки очищаются адресно. `NOREPLY` не создаёт итог.
Права, точные question ID, account/chat/thread/message-проверки и защита
секретов сохраняются. Метаданные страницы не дают чужой карточке доступ к
результату.

Короткие варианты и описания отображаются в штатном списке формы один раз.
Длинные формулировки остаются полностью доступны над сокращёнными кнопками.
Обычный вариант вместе с непустым своим текстом возвращает ошибку у поля:
форма сохраняет написанное, пока человек не очистит поле или не выберет
«Свой ответ». Неподтверждённый текст не теряется молча.

Статус и Stop независимы для каждого исходного треда. Если Codex временно не
подтвердил запрос, существующие карточки показывают «Проверяю состояние
Codex» с ранее опубликованными шагами. Rele продолжает сверку без повторной
отправки задачи; неизвестное состояние не выдаётся за выполнение.

Перед отправкой busy сохраняется адрес исходного треда. После перезапуска
Rele пересчитывает его статус по текущим запросам и снимает прежний индикатор,
когда работа завершена. Потерянный ACK очистки допускает повтор адресного
обновления статуса, без повторной отправки задачи или итога.

Если typed async-событие опередило общую историю, вопрос сверяется по
каноническому question ID, содержимому и turn ID. Незавершённая проверка
принадлежности или отмена блокирует такую публикацию; смешанные ходы не
экспортируются.

Используются штатные [task_card](https://docs.slack.dev/reference/block-kit/blocks/task-card-block/)
и [chat.update](https://docs.slack.dev/reference/methods/chat.update/).
Итог разбит с учётом лимита [Markdown-блоков](https://docs.slack.dev/reference/block-kit/blocks/markdown-block/).
Source-тесты, проверки compiled-кода с синтетическими событиями и реальная
проверка Slack desktop/mobile являются разными доказательствами. Критерии
RC6 перечислены в [ACCEPTANCE.md](ACCEPTANCE.md); этот документ не фиксирует
их прохождение.
