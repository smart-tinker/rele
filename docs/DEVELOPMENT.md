# Разработка, проверка и выпуск Rele

GitHub Actions не используется: бесплатный лимит не расходуется ни на обычные
изменения, ни на выпуск. Не запускать `workflow_dispatch`, rerun или автоматику
запуска workflow. Проверки и сборки выполняются существующими локальными scripts.

## Рабочий цикл

1. Согласовать цель, границы изменения и тестовые среды. Обычная реализация,
   исправления, целевые тесты, пересборки, передача исходников и скриптов на
   согласованные стенды входят в этот цикл. Новое разрешение на каждую такую
   итерацию не требуется. Commit/SHA и хеши файлов подтверждают целостность
   конкретной итерации, а не создают новый запрос разрешения.
2. Работать в отдельной ветке/worktree. Сначала выполнять проверки изменённого
   участка и review готового diff. При сбое сначала проверять проблемный primitive
   или stage; не повторять полную сборку и матрицу ради каждой диагностической
   правки.
3. Заморозить RC и выполнить обязательную итоговую матрицу на **обоих** стендах:
   **windows-test-host — Windows**, **linux-test-host — Ubuntu Server**. Использовать штатные пакеты
   и установщики из `scripts/package.mjs`, `scripts/build-windows-installer.mjs`
   и `scripts/build-linux-installer.mjs`. Unit/native/browser, installer/recovery,
   Windows owner/SID/ACL/DPAPI и Linux systemd проверяются в подходящей среде;
   SSH session 0 не заменяет интерактивный сеанс владельца Windows. Полный состав
   и отдельная GUI/мессенджерная приёмка описаны в [ACCEPTANCE.md](ACCEPTANCE.md).
4. Связать результаты с commit сборки, версиями инструментов и SHA256 пакетов.
   Проверенный diff проходит PR и попадает в main; публикуемый RC содержит
   именно проверенные байты. Сборка до merge допустима: соответствие её исходников
   принятому коду main и неизменность артефактов должны быть подтверждены.
   Новый diff, сбой или изменение среды требуют соответствующей перепроверки;
   узкий probe не подменяет обязательную итоговую приёмку RC.
5. Переход к stable и согласованное обновление остальных машин выполняются
   только после приёмки RC. Публикация, локальная установка, подключение runtime
   и реальная доставка в мессенджер фиксируются как разные результаты.

Согласованный scope определяет разрешённые действия; этот документ не расширяет
его на другие машины, рабочие профили или несогласованные операции. Отказ
автоматической проверки разрешений обязателен: его нельзя обходить или считать
снятым этим стандартом. Причину и оставшуюся границу нужно сообщить пользователю;
разрешённую независимую работу можно продолжать.

Секреты, auth и частная история не попадают в исходники, пакеты и публичные отчёты.
Тестовые fixture используют отдельные профили и локальный provider. Для native
проверок переиспользуются `scripts/protocol-probe.py`,
`scripts/managed-protocol-probe.py` и `scripts/shared-protocol-probe.py`.
