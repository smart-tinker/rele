# Разработка, проверка и выпуск Rele

Разработка ведётся через GitHub issues и PR. На PR и push в main CI выполняет
установку зависимостей, typecheck, unit-тесты и build на стандартных
`ubuntu-24.04` и `windows-2025`. Новые push отменяют устаревшие обычные проверки.
Полная матрица пакетов, native/protocol, voice и browser проверок запускается
вручную через `workflow_dispatch`; `native_only` оставляет узкую диагностику.

Все jobs разрешены только в **публичном** репозитории. Пока он приватный,
workflow не запускать: подготовка CI не является разрешением раскрывать историю.
Стандартные hosted runners публичных репозиториев бесплатны; larger runners
не использовать. Кэш npm и загрузка Actions artifacts отключены: результаты
проверок доступны в логах, пакеты полной проверки временные и не публикуются.
Текущий CI не заменяет процесс выпуска проверенных байтов и приёмку RC.
[Правила оплаты GitHub](https://docs.github.com/en/billing/concepts/product-billing/github-actions).
Эта конфигурация не удаляет старые artifacts и не меняет billing budgets аккаунта.

До завершения перехода выпуск сохраняет существующий сборочный маршрут:
**Windows — windows-test-host**, **Linux — linux-build-host**, в изолированных build-каталогах.
Для Windows используется Windows-окружение; Wine на linux-build-host не нужен.

Приёмка — отдельный этап: **windows-test-host — Windows**, **linux-test-host — Linux**.
Он проверяет только готовое установленное приложение или штатный portable.
windows-test-host совмещает роли сборки и приёмки, но этапы и каталоги разделены:
исходники и dev-зависимости из build-каталога не подмешиваются в проверяемый пакет.
linux-build-host остаётся Linux-builder и не используется для приёмки этого RC.
В этапе приёмки не запускаются `npm ci`, typecheck, Vitest, компиляция или
build/package scripts. **linux-test-host используется только для приёмки**: туда передаются
готовые installers/portable и узкие операторские скрипты, без исходников репозитория
и dev-окружения.

## Рабочий цикл

1. Зарегистрировать проблему в issue: проверить дубли, выполнить triage и определить
   критерии приёмки. Включить выбранные issues в согласованный scope выпуска;
   milestone можно использовать для группировки, но он не обязателен.
2. Согласовать цель, границы изменения и тестовые среды. Обычная реализация,
   исправления, целевые тесты, передача исходников/скриптов в согласованные
   build-каталоги и пересборки входят в этот цикл. В этап приёмки передаются готовые installers/portable
   и узкие операторские preflight/install/postflight-скрипты без исходников
   приложения и секретов. Новое разрешение на каждую такую
   итерацию не требуется. Commit/SHA и хеши файлов подтверждают целостность
   конкретной итерации, а не создают новый запрос разрешения.
   Работать в отдельной ветке/worktree и связать PR с issues через `Refs #…`.
   Не использовать автозакрывающие `Fixes`/`Closes`: merge ещё не означает приёмку.
   Сначала выполнять проверки изменённого
   участка и review готового diff. При сбое сначала проверять проблемный primitive
   или stage; не повторять полную сборку и матрицу ради каждой диагностической
   правки.
3. Заморозить RC и завершить обязательные unit/native/browser-проверки и сборку
   штатных пакетов в build-каталогах windows-test-host и linux-build-host. Зафиксировать commit сборки,
   версии инструментов и SHA256 пакетов. Новый diff, сбой или изменение среды
   требуют соответствующей перепроверки; узкий probe не заменяет итоговые gates.
4. Провести PR через review и main, затем опубликовать RC с проверенными байтами.
   Сборка до merge допустима при подтверждённом соответствии её исходников
   принятому коду main. Опубликованные assets/tag RC неизменяемы: последующие
   исправления выпускаются следующим RC, а не заменяют прежний пакет.
5. После публикации RC в этапе приёмки на windows-test-host и linux-test-host
   проверить SHA256 полученных installers/portable, установить готовое приложение
   и выполнить приёмку его работы, обновления и восстановления. Windows
   owner/SID/ACL/DPAPI проверяются в интерактивном сеансе владельца; SSH session 0
   его не заменяет. Linux systemd проверяется на linux-test-host. Операторские
   скрипты работают с готовым приложением, не запускают source/dev-suite.
   Полный состав описан в [ACCEPTANCE.md](ACCEPTANCE.md).
6. Закрыть issue только после выполнения и принятия его критериев, со ссылкой
   на проверенный RC и evidence. Непроверенные критерии оставляют issue открытым.
   Переход к stable и согласованное обновление остальных машин выполняются
   только после приёмки RC и согласования этого этапа. Публикация, локальная установка, подключение runtime
   и реальная доставка в мессенджер фиксируются как разные результаты.

Согласованный scope определяет разрешённые действия; этот документ не расширяет
его на другие машины, рабочие профили или несогласованные операции. Отказ
автоматической проверки разрешений обязателен: его нельзя обходить или считать
снятым этим стандартом. Причину и оставшуюся границу нужно сообщить пользователю;
разрешённую независимую работу можно продолжать.

Секреты, auth и частная история не попадают в исходники, пакеты и публичные отчёты.
Source fixture в build-каталогах используют отдельные тестовые профили и локальный
provider. Там переиспользуются `scripts/protocol-probe.py`,
`scripts/managed-protocol-probe.py` и `scripts/shared-protocol-probe.py`;
их dev-окружение не используется для приёмки установленного приложения.
Рабочие auth и история Codex не копируются в build- или тестовые профили.
