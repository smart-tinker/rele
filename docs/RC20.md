# Rele 0.1.1-rc.20

Windows Desktop подключается к общему native app-server напрямую по loopback WebSocket. Установщик меняет только принадлежащий Rele адрес `CODEX_APP_SERVER_WS_URL`; прежние собственные CLI_PATH/FORCE_CLI восстанавливаются по сохранённым значениям. Адаптер между Desktop и сервером, отдельный CLI и копирование профиля не нужны. После первого подключения уже открытый private Desktop требует одного полного Quit и обычного запуска.

Независимая задача текущего Windows-пользователя запускает backend установленного Desktop/CLI при входе и восстанавливает его минутным триггером с IgnoreNew. Работающий экземпляр сохраняется. Прежняя собственная задача без такого триггера обновляется без остановки живого сервера. Маленький immutable ProcessHost остаётся вне обновляемой папки Rele. Контроллер проверяет SID, executable/hash, время рождения процесса, PID владельца порта и исходный профиль. Обновление Rele сохраняет живой сервер; удаление восстанавливает собственный адрес и отменяет будущий автозапуск, сохраняя текущих клиентов. Ubuntu использует прежний штатный daemon/UDS: обычная команда `codex` не подменяется.

После Stop Rele автоматически продолжает единственную подтверждённую собственную запись native-очереди. Чужая или смешанная очередь остаётся защищённой от запуска. Для отменённой собственной shell-команды проверяется завершение native terminal и дочернего процесса до освобождения запроса и запуска следующего. Потерянный ответ управления сверяется; после потери исходного connection/Engine epoch неподтверждённый cleanup остаётся неопределённым, PID вслепую не повторяется.

Windows адрес-only Desktop не передаёт Bearer. Поэтому локальный RC слушает только `127.0.0.1` без токена и доступен другим локальным процессам и пользователям машины. Порт нельзя открывать в сеть. Native WebSocket upstream остаётся экспериментальным; native terminate не предоставляет atomic expected-item/turn CAS.

Результаты для точного commit и пакетов приводятся в GitHub release. Реальные Slack/Telegram, управление с телефона, reboot и длительная эксплуатация остаются отдельной пользовательской приёмкой из [ACCEPTANCE.md](ACCEPTANCE.md). Проверки с synthetic provider/source не выдаются за эту приёмку. Windows RC без подписи издателя.

## Известные ограничения

- [Issue #1](https://github.com/smart-tinker/rele/issues/1): поддерживаемые версии Codex не привязывают native Goal-запись к состоянию, показанному в Slack. Создание может заменить цель, появившуюся после открытия формы; остановка может приостановить другую текущую цель. Поэтому создание и остановка из Slack отключены до безопасной native-возможности. Чтение Goal, Status, Model и обработка уже существующих квитанций остаются доступны. Issue остаётся открытым для safe-write поддержки и реальной Slack Desktop/mobile приёмки.
- [Issue #26](https://github.com/smart-tinker/rele/issues/26) остаётся открытым по историческому cleanup stage: исходный [Windows run #43375287426](https://github.com/smart-tinker/rele/actions/runs/43375287426) сохранил только агрегированный `TimeoutError()` и не установил операцию, длительность или процесс, вызвавший timeout. Поздний [run #44227151928](https://github.com/smart-tinker/rele/actions/runs/44227151928) отдельно записал `EngineDriver.read` timeout и ошибку `engine-close-ack` после 17,335 ms; он не доказывает причину или точный этап исходного инцидента. Исторический этап восстановить нельзя.
