# RC30 — управляемое обновление и проверяемая очистка

Панель различает работающий сервер Codex, выбранную версию и новейшую найденную установку. Автоматическая политика выбирает максимум среди уже установленных поддерживаемых версий; ручная закрепляет установку. Сохранение политики не меняет работающий сервер. Rele не скачивает Desktop/MSIX, и Windows Store может предложить новую версию позже.

Обновление проходит через подготовку, завершение задач и явное подтверждение закрытых клиентов. При занятом сервере или открытом клиенте отказ допускает повтор, сохраняя очередь. После успеха можно снова открыть клиенты Codex без перезагрузки Windows. Linux использует этот путь для штатного native daemon начиная с проверенного исходного backend `0.166.0-alpha.5.1`; более ранний backend получает отказ до остановки; произвольная внешняя служба автоматически не заменяется.

После проверенного подключения Windows native `codex-postflight` удаляет только доказанно ненужные собственные остатки. Текущие и используемые файлы, recovery references, профиль, история и auth сохраняются; неизвестное остаётся с причиной. Компактный итог очистки доступен в технических сведениях. Inno самостоятельно удаляет свой временный каталог, dpkg заменяет старый payload. На Linux устаревшие native-пакеты обрабатывает штатный updater Codex; число удалённых им файлов Rele не выдумывает. Нового общего GC для WindowsApps, NVM или чужих пакетов нет.

Для ошибки установки Windows `0x80073D02` технические сведения объясняют, что пакет может удерживать sandbox service: одного закрытия Desktop бывает недостаточно. Требуется штатное обновление Windows или пакета; Rele не завершает SYSTEM-службу ради установки MSIX.

Открытое WebSocket-соединение проверяется через ping/pong. При отсутствии ответа Rele снимает статус подключения и повторяет только подключение. После таймаута RPC одна короткая проверка `server/diagnostics` отличает медленный запрос от неотвечающего сервера; на время проверки новые отправки приостановлены. Неподтверждённый запрос не повторяется автоматически, native-процесс не завершается.

Rele различает превышение контекста и отказ автоматического сжатия Codex из-за лимита модели. Причина определяется по native-ошибке исходного запроса, а не по тексту ответа ассистента. Такой запрос не получает автоматических повторов как при перегрузке; Rele не меняет модель и не создаёт новый разговор. Сообщение об ошибке не означает, что причина отказа native-сжатия устранена.

Повторная загрузка контекста сравнивает исходное сообщение и его содержимое,
а не случайный Slack `block_id` или идентификатор доставки. Изменения текста,
вложений и файлов сохраняются; одинаковый текст разных сообщений не объединяется.
При обновлении старые записи журнала и их точные квитанции остаются на месте,
повторные версии исключаются из новой передачи. Потерянный ACK сверяется по
первоначальным записям, включая старые эквивалентные доставки.

В RC30 пассивные сообщения получали ID с префиксом `msg_`. Он может попадать
в запрос к провайдеру как ссылка на сохранённый item, поэтому прежнее утверждение
о его совместимости было неверным. В кандидате 0.1.1-rc.1 новые сообщения получают
локальный ID `rele-context-…` без подчёркиваний: проверенный native Codex 0.166
сохраняет его для квитанции, но исключает из копии сообщения для провайдера.
Старые `msg_` и `rele_slack_` по-прежнему учитываются при проверке точных квитанций;
их ID, авторство и история не переписываются. Вся беседа и рабочее сжатие остаются
в Codex; журнал Rele служит доставке. [Изменения 0.1.1-rc.1](0.1.1-rc.1.md).

RC30 вошёл в опубликованный стабильный 0.1.0. Кандидат 0.1.1-rc.1 пока не опубликован; его проверка начинается на Windows test host. Обновление остальных машин определяется результатами приёмки. Результаты конкретных исходников, пакетов и целевых систем фиксируются в release evidence. Проверки подключения не заменяют native или GUI-приёмку и не устанавливают причину зависания native.
